# RBAC yang benar dengan better-auth — riset sumber primer

Tanggal: 2026-09-03. better-auth terinstall: `1.7.1` (`packages/backend/package.json`, `node_modules/better-auth/package.json`).
Scope repo: `packages/backend/src/modules/auth/index.ts` (betterAuth + `admin()` + macro Elysia `auth`/`admin`), `utils/role.ts` (`hasRole` split koma), `tables/auth.table.ts` (`users.role` text nullable).

Konvensi di bawah: **"Kata docs/source"** = klaim faktual dengan sitasi; **"Interpretasi"** = opini/rekomendasi penulis laporan, bukan klaim docs.

## (a) Model role resmi better-auth

- **Kata docs:** hanya ada dua role bawaan: `admin` (kontrol penuh atas user lain) dan `user` (tidak punya kontrol atas user lain). — `https://www.better-auth.com/docs/plugins/admin` § Roles.
- **Kata docs:** seorang user bisa memegang **multiple roles**, disimpan sebagai **string dipisahkan koma** (`","`). — docs admin § Roles, Callout. Source: `node_modules/better-auth/dist/plugins/admin/has-permission.mjs` fungsi `hasPermission` — `(input.role || defaultRole || "user").split(",")`, lalu loop tiap role dan `acRoles[role]?.authorize(...)`.
- **Kata source:** penyimpanan write-path selalu dinormalisasi ke format koma: `parseRoles` = `Array.isArray(roles) ? roles.join(",") : roles` — `node_modules/better-auth/dist/plugins/admin/routes.mjs:22-24`, dipakai di `setRole` (`:77`), `createUser` (`:199`).
- **Kata docs:** `defaultRole` default `"user"`; `adminRoles` default `["admin"]`. — docs admin § Options (Default Role, Admin Roles). Source default: `node_modules/better-auth/dist/plugins/admin/admin.mjs` — `defaultRole: options?.defaultRole ?? "user"`, `adminRoles: options?.adminRoles ?? ["admin"]`.
- **Kata docs/source:** `adminRoles` kustom (mis. `superadmin`) **harus didefinisikan** di access control kustom (`ac` + `roles`); bila tidak, constructor melempar `BetterAuthError("Invalid admin roles...")`. — `admin.mjs` blok validasi `invalidRoles`; docs admin § Admin Roles + Callout warning.
- **Kata docs:** saat **tidak** memakai access control kustom, hanya `admin` dan `user` yang valid; role di luar daftar `adminRoles` **tidak bisa** melakukan operasi admin. — docs admin § Admin Roles, warning.
- **Kata source:** peran `adminUserIds: string[]` (default `[]`) adalah jalur admin kedua, independen dari kolom `role`: `hasPermission` me-return `true` bila `input.options?.adminUserIds?.includes(input.userId)` — `has-permission.mjs`; docs admin § Admin userIds.
- **Kata source:** permission bawaan resource `user`: `create, list, set-role, ban, impersonate, impersonate-admins, delete, set-password, set-email, get, update`; `session`: `list, revoke, delete`. Role `admin` mendapat semuanya **kecuali** `impersonate-admins`; role `user` tidak mendapat apa pun. — `node_modules/better-auth/dist/plugins/admin/access/statement.mjs` (`defaultStatements`, `adminAc`, `userAc`).
- **Kata source:** skema plugin menambah ke tabel `user`: `role: string optional`, `banned: boolean default false`, `banReason: string optional`, `banExpires: date optional` (semua `input: false`); ke tabel `session`: `impersonatedBy: string optional`. — `node_modules/better-auth/dist/plugins/admin/schema.mjs`.
- **Kata docs:** `admin()` juga meng-inject `databaseHooks.user.create.before` yang mengisi `role: defaultRole ?? "user"` bila field kosong. — `admin.mjs` blok `init()` → `databaseHooks`. (Repo ini menimpa/menambah hook sendiri — lihat §e.)
- **Interpretasi:** model resmi = **satu kolom string koma** + access-control `ac` opsional. Tidak ada tabel join role/permission bawaan. Untuk kebutuhan repo (satu label `admin`), model bawaan sudah cukup; `ac` kustom baru diperlukan bila muncul permission non-user-management (mis. `project:create` ala contoh docs).

## (b) Cara cek role yang benar di server (session vs re-query, staleness)

- **Kata source:** setiap endpoint `/admin/*` dijaga dua lapis: (1) `adminMiddleware` = `getAuthoritativeSessionFromCtx(ctx)`, unauthorized bila tidak ada session; (2) `hasPermission({ userId, role: session.user.role, options, permissions })` per-endpoint (mis. `setRole` menuntut `user: ["set-role"]`, `banUser` menuntut `user: ["ban"]`). — `routes.mjs:17-21` + tiap handler (`:65-69`, `:526-531`, dst.).
- **Kata source:** `getAuthoritativeSessionFromCtx` pada deployment **stateful** (ada DB session store, seperti repo ini via drizzleAdapter) **me-reset `ctx.context.session = null` lalu memaksa `disableCookieCache: true`** — yaitu baca otoritatif dari DB, bukan dari cookie cache. Pada deployment stateless, cookie adalah otoritas. — `node_modules/better-auth/dist/api/routes/session.mjs:236-281` (`isStateful`, `getAuthoritativeSessionFromCtx`).
- **Kata source:** `GET /get-session` (yang dipakai `auth.api.getSession({ headers })` di macro repo) punya jalur **cookie cache**: bila `session.cookieCache.enabled` dan payload cookie valid/belum kedaluwarsa, ia me-return data cookie **tanpa query DB** (`findSession` tidak dipanggil). Jalur DB (`internalAdapter.findSession(sessionCookieToken)`) hanya terjadi saat cache miss/disabled. — `session.mjs:44-148` (jalur cache) vs `:148` (`findSession`).
- **Interpretasi:** `auth.api.getSession({ headers })` itu **nyaman tapi berpotensi stale** untuk `role` (dan `banned`) selama jendela cookie-cache. Pola resmi untuk keputusan sensitif adalah `getAuthoritativeSessionFromCtx` (dipakai semua endpoint admin bawaan) atau `auth.api.userHasPermission({ body: { userId/role, permissions } })` — endpoint `POST /admin/has-permission`, yang menerima `role` langsung (server-only) atau `userId`. — docs admin § Access Control Usage; `routes.mjs` ekspor `userHasPermission`.
- **Interpretasi (rekomendasi guard):** untuk guard RBAC generik, tiru urutan resmi: (1) ambil session otoritatif (bypass cookie cache saat stateful), (2) cek `role` via `hasPermission`-setara/`userHasPermission`, bukan `string.includes` mentah. Pengecekan `role` dari objek session hasil `getSession` standar dapat diterima untuk route non-sensitif, tapi untuk keputusan admin/sensitif gunakan jalur otoritatif.

## (c) Banned/banExpires + emailVerified di guard

- **Kata source (ban saat pembuatan session):** `admin()` mendaftarkan `databaseHooks.session.create.before`: bila `user.banned` true → cek `banExpires`: bila sudah lewat, **auto-unban** (`banned:false, banReason:null, banExpires:null`) dan lanjut; bila masih berlaku, lempar `FORBIDDEN / BANNED_USER` dengan `bannedUserMessage`. — `admin.mjs` blok `init()` → `session.create.before`.
- **Kata docs:** `banUser` mencegah user sign-in dan **mencabut semua session existing**; `banExpiresIn` dalam detik, opsional (tanpa itu = permanen). — docs admin § Ban User. Opsi terkait: `defaultBanReason` (default `"No reason"` — hmm, docs Options menulis `"Spamming"` sebagai contoh nilai, bukan default harfiah; yang pasti ada opsi ini), `defaultBanExpiresIn`, `bannedUserMessage`. — docs admin § Options.
- **Kata source (sign-in):** bila `emailAndPassword.requireEmailVerification && !user.emailVerified` → lempar `FORBIDDEN / EMAIL_NOT_VERIFIED` (dan opsional kirim ulang email bila `sendOnSignIn`). Tidak ada session yang dibuat. — `node_modules/better-auth/dist/api/routes/sign-in.mjs:339-356`.
- **Kata source (sign-up):** bila `requireEmailVerification` true (atau `autoSignIn === false`), respons sign-up adalah generic-duplicate-safe dan **auto-sign-in dilewati** (`shouldSkipAutoSignIn`), lalu verification email dikirim bila `sendOnSignUp`/require. — `node_modules/better-auth/dist/api/routes/sign-up.mjs:163-164, :250-260`.
- **Interpretasi:** guard repo yang benar minimal tiga lapis berurutan: (1) ada session otoritatif, else 401; (2) tolak bila `user.banned` masih berlaku (bandingkan `banExpires` vs now; bila kedaluwarsa anggap un-banned mengikuti perilaku hook resmi) → 403; (3) tolak bila `!user.emailVerified` → 401 (konsisten dengan ADR-0002: Session hanya valid setelah Verification). Cek `banned`/`emailVerified` dari **session otoritatif/DB**, bukan dari cookie cache, karena keduanya bisa berubah pasca-login (ban oleh admin; verifikasi email menyusul).

## (d) Pola Elysia macro/guard yang direkomendasikan untuk RBAC generik

- **Kata docs Elysia:** macro adalah fungsi/obejk yang mengontrol lifecycle, skema, dan konteks per-route; diaktifkan via properti hook (mis. `{ auth: true }`). — `https://elysiajs.com/patterns/macro.html` § Macro.
- **Kata docs Elysia:** untuk error HTTP dari macro, **return `status(401/403, ...)`** (bukan `throw`), agar status teranotasi benar untuk Eden/OpenAPI type-gen. Macro mendukung `resolve` untuk menambah properti konteks (mis. `user`, `session`) dan bisa **extend macro lain** (`admin` memakai `auth: true` lalu `resolve` lanjutan). — `elysiajs.com/patterns/macro.html` § Error handling, § Resolve, § Extension; catatan limitasi inferensi TS untuk macro-yang-extend-macro (gunakan named single macro bila perlu inferensi di dalam `resolve`).
- **Kata docs Elysia:** `guard` menerapkan hook+schema ke banyak route sekaligus; `group(prefix, guard, scope)` untuk prefix. Alternatif: `beforeHandle`/`resolve` dengan `as: "scoped"|"global"` untuk menaikkan scope lifecycle ke parent. — `https://elysiajs.com/essential/plugin.html` § Guard, § Scope.
- **Interpretasi (pola generik, bukan hardcoded admin):** buat **satu macro berparameter**, mis. `requireRole(role | string[])` atau `requirePermission(resource, actions)`, yang extend macro `auth` (session otoritatif) lalu di `resolve`-nya menjalankan cek permission setara-`hasPermission` dan `return status(403)` bila gagal. Daftarkan macro di plugin auth instance (`new Elysia({ name: "auth" })`), lalu pakai per-route (`{ requireRole: "admin" }`) atau per-grup via `guard`/`group("/admin", { requireRole: "admin" }, ...)`. Ini menggantikan macro `admin` hardcoded dengan tetap memakai idiom macro resmi.

## (e) Celah implementasi repo saat ini vs docs resmi

1. **`hasRole` split-tanpa-trim vs normalisasi resmi.** `utils/role.ts:1-2` memakai `user.role?.split(",").includes(role)` — tanpa `trim()`, tanpa case-fold. Source resmi men-trim saat membandingkan `adminRoles` (`routes.mjs:587` — `.map(r => r.trim())`) dan membandingkan case-insensitive saat validasi (`admin.mjs` — `toLowerCase()`). **Interpretasi:** `"admin, editor"` (dengan spasi) atau `"Admin"` lolos di guard resmi tapi gagal di `hasRole` repo → inkonsistensi penolakan yang sah. Bukan kata docs bahwa trim wajib; ini celah vs perilaku source resmi.
2. **Guard memakai session non-otoritatif.** Macro `auth` di `index.ts:216-226` memanggil `auth.api.getSession({ headers })` (jalur cookie-cache, §b) dan macro `admin` (`:227-234`) hanya cek `hasRole(user, "admin")`. Endpoint `/admin/*` bawaan memakai `getAuthoritativeSessionFromCtx` (bypass cache). **Interpretasi:** perubahan `role`/`banned` pasca-login bisa tidak terlihat guard repo selama jendela cache.
3. **`admin()` dipanggil tanpa opsi + tanpa `ac`/`roles`.** `index.ts:152` — `admin()`. **Kata docs:** default `defaultRole "user"`, `adminRoles ["admin"]` — jadi fungsional untuk kasus tunggal, tapi: (a) proteksi impersonasi antar-admin mengandalkan default (target ber-role admin butuh permission `impersonate-admins` yang tidak dimiliki `adminAc` — `routes.mjs:587-593`, `statement.mjs`); (b) permission `user`-management penuh melekat pada siapa pun ber-role `admin` tanpa granularitas. **Interpretasi:** acceptable untuk bootstrap satu-admin, rapuh bila role bertambah.
4. **Hook first-user meniru sebagian perilaku resmi.** `index.ts:168-175` — `user.create.after` menghitung `count(users) === 1` lalu `set({ role: "admin" })`. **Kata source:** hook resmi adalah `user.create.before` yang mengisi `role: defaultRole` (`admin.mjs`); repo tidak memakai `adminUserIds`/`create-admin` CLI resmi (docs admin § Usage: `bun x auth@latest create-admin ...`, email admin default terverifikasi). **Kata ADR-0002:** repo sengaja menghapus `emailVerified: true` dari hook dan mematikan `autoSignIn` agar Verification wajib — tetapi **kode saat ini (`index.ts:100` `autoSignIn: true`) belum mencerminkan keputusan ADR** (ADR menyebut `autoSignIn: false` + gate `emailVerified` di macro `auth`; macro saat ini di `:216-226` belum mengecek `emailVerified`). **Interpretasi:** drift ADR-vs-kode: klaim CONTEXT.md ("Session hanya valid setelah Verification, enforced in the `auth` macro") tidak ditegakkan kode macro saat ini.
5. **Tidak ada pengecekan `banned`/`banExpires` di guard repo.** Kolom ada di skema (`auth.table.ts:12-14`) dan hook session-create resmi menolak banned user, tetapi session yang **sudah berjalan saat di-ban** hanya tertangani bila endpoint memakai sesi otoritatif + guard memeriksa flag — macro repo tidak memeriksa. **Kata docs:** `banUser` mencabut semua session existing; guard yang hanya membaca cookie cache bisa tetap meloloskan hingga cache kedaluwarsa. (Revokasi server-side tetap terjadi; ini soal jendela keterlihatan guard.)
6. **Tidak ada `customSyntheticUser`.** **Kata docs** (admin § Schema → Email Enumeration Protection): bila memakai enumeration protection (`requireEmailVerification` atau `autoSignIn: false` — repo memakai keduanya secara intended), perlu `customSyntheticUser` yang menyertakan field plugin admin (`role, banned, banReason, banExpires`) pada respons sign-up palsu. Repo (`index.ts:86-151`) tidak mengonfigurasi ini. **Interpretasi:** respons fake sign-up bisa bocor/skema-tidak-konsisten vs user asli.
7. **Impersonasi aktif tanpa guard sesi di repo.** **Kata source:** kolom `impersonatedBy` ada (`auth.table.ts:28`, `schema.mjs` session); endpoint `/admin/impersonate-user` membuat session 1 jam (default, `routes.mjs:598`) dan `/list-sessions` menyembunyikan session impersonasi (`admin.mjs` hooks.after). Guard repo tidak membedakan session impersonasi. **Interpretasi:** untuk aksi sensitif, pertimbangkan menolak/menandai `session.impersonatedBy` — pola ini tidak diwajibkan docs, tapi konsisten dengan model session resmi.

## (f) Opsi yang TIDAK direkomendasikan docs resmi

- **Jangan mengarang role bebas tanpa `ac`/`roles` saat non-default.** Kata docs: tanpa access control kustom, hanya `admin`/`user` yang valid; role lain di luar `adminRoles` tidak bisa operasi admin — dan `adminRoles` kustom yang tidak terdaftar di `roles` melempar saat init. — docs admin § Admin Roles; `admin.mjs` validasi.
- **Jangan andalkan cek role client-side untuk otorisasi.** Kata docs: `checkRolePermission` di client bersifat **sinkron dan hanya memeriksa definisi role**, bukan permission user yang login ("does not check the permissions of the currently logged-in user directly"). Otorisasi harus via `hasPermission`/`userHasPermission` server-side atau `hasPermission` di handler endpoint. — docs admin § Access Control Usage.
- **Jangan izinkan `impersonate-admins` ke role admin biasa.** Kata source: `adminAc` bawaan **sengaja tidak** menyertakan `impersonate-admins` (ada di `defaultStatements` tapi tidak di `adminAc.statements`), dan `impersonateUser` menolak impersonasi target ber-role admin kecuali pemanggil punya permission itu (`routes.mjs:587-593`). Memberikannya ke `admin` meniadakan proteksi default. — `statement.mjs`, `routes.mjs`.
- **Jangan berharap `adminRoles` saja cukup saat memakai `ac` kustom.** Kata docs (Callout § Admin Roles): opsi `adminRoles` **tidak diperlukan** saat memakai `ac`+`roles` — yang berlaku adalah permission yang diberikan eksplisit per role. Mencampur kedua mental model (daftar admin vs matriks permission) adalah sumber misconfig resmi yang didokumentasikan.
- **Jangan lewatkan migrasi skema plugin.** Kata docs: setelah menambah plugin, jalankan migrasi/generate (`auth migrate`/`auth generate`) agar kolom `role/banned/banReason/banExpires/impersonatedBy` ada. Guard tanpa kolom = cek terhadap `null`/`undefined`. — docs admin § Installation + § Schema.
